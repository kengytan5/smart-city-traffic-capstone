**Architecture Tracking \& Logging Configuration**



1. This project implements a professional, centralized logging structure via Python’s native logging library. To completely satisfy project constraints, it avoids root logging errors by instantiating module-isolated logger handles (logging.getLogger(\_\_name\_\_)) across every file component. All tasks write and append their logs directly into a single, consolidated file: pipeline.log.
2. Logging Blueprint Formatter Layout

&#x20;  Every log event across all operational scripts is tracked via this strict, explicit blueprint layout:

&#x20;  %(asctime)s \[%(levelname)s] %(name)s: %(message)s

&#x20;  Example Output: 2026-10-31 09:17:11 \[INFO] visualizations: Successfully saved figure 1...



3\. Meaningful Level Assignments Used

&#x20;  DEBUG:   Fine-grained background variables and intermediate calculation values (such as mathematical min-max scaling constraints, Z-score standard deviation matrices, and

&#x20;           statistical quartile boundaries) useful exclusively for developer system auditing. These entries remain completely hidden unless the core logger level threshold is

&#x20;           explicitly dialed down to DEBUG.

&#x20;  INFO:    Documents normal, expected structural pipeline milestones, processing checkpoints, data file loading successes, function completions, and visual figure export paths.

&#x20;  WARNING: Tracks unpredicted but safely recoverable dataset anomalies, such as row deduplication extractions, unphysical 0 Kelvin temperature updates, or physically impossible

&#x20;           precipitation sensor overrides.

&#x20;  ERROR:   Preserves critical runtime script failures or corrupted file inputs, mapping a clean system stack trace to the log file before executing a graceful shutdown hook to

&#x20;           avoid a raw system crash.





**Smart City Drift Monitoring \& System Alerting Rules**



The monitoring script (monitoring/MLOps and Deployment Simulation.py) actively assesses production data streams for performance decay using two discrete validation metrics:



1. Feature Distribution Drift

&#x20;  Checks incoming temperature variables against the historical data baseline average of 281.27 Kelvin. If the live rolling average shifts past a strict variance tolerance of 15.0 Kelvin, a drift state is flagged.



2\. Prediction Error Drift

&#x20;  Tracks live model performance accuracy bounds. If the mean prediction error breaks past a ceiling threshold of 1000.0 MAE vehicles, an accuracy degradation state is flagged.





Operational Dashboard Alert Outcomes



🟢 PASS / Normal Baseline Operations

&#x20;   Dispatched when all streaming feature values and prediction error scales hold nominal positions within safe tolerance matrices.



🚨 ALERT / Requires Immediate System Investigation

&#x20;   Triggered the moment input distributions warp or accuracy decays past guard boundaries. The system automatically outputs a warning alert block to the console dashboard and appends an immediate notice to the log history file.





**Data Source Transparency Declaration**



⚠️ Accident Dataset Proxy Note

&#x20;  In strict compliance with capstone project safety and transparency guidelines, it is explicitly stated that no real-world vehicle accident dataset was provided for this capstone.





To demonstrate classification models, feature pipelines, and deep learning workflows reliably, a proxy target column named 'high\_risk' was synthetically engineered from the available features. This label combines high or severe traffic volume quartiles with active, severe convective weather states ('Rain', 'Snow', 'Thunderstorm', 'Squall') or visibility-restricting environmental features ('Fog', 'Haze', 'Mist', 'Smoke'). This vector is used exclusively as a proxy for machine learning classification practice workflows and does not reflect predictions of actual physical accident locations or events.
